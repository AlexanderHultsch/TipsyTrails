# Tipsy Trails — the iOS branch's contract with `main`

**Applies to:** branch `ios-app`
**Companions:** `ios/SPEC.md` (what the app is), `SPEC.md` at the repository root (what the parent is)
**Enforced by:** `packages/shared/src/ios-parent-pin.test.ts`

---

## What this is

Website development continues on `main`. `ios-app` has to follow it, and the obvious way to make that possible — a file listing every change on `main` and every debugging step, so the iOS branch can keep up — is the one thing this repository has already proved does not work.

It has the scars. `HANDOVER.md` carried "SPEC.md is now v1.11" for forty-one versions, on a file whose own opening paragraph asks the reader to keep it current, because it was a hand-maintained copy nothing could check. A test count in the same file rotted the same way and was deleted rather than pinned, because no test could hold it honestly. A log of every change on `main` would be a third hand-maintained copy, and it would be mostly noise: nothing in v1.46–v1.58 — rate-limit bucket keys, the app-shell bundle budget, licence paths, Definition-of-Done bookkeeping — touches the tracker at all. A log that is mostly noise stops being read, and then it is worse than nothing, because it still looks authoritative.

So there is no log. There are three things instead, and each of them is small enough to stay true:

1. **A dependency surface** (Section 1). The list of what the iOS app actually depends on in the parent. It turns the question a reader cannot answer — _"is this change relevant to iOS?"_ — into one they can: _"did I touch anything on this list?"_
2. **A merge record** (Section 3). One row per merge of `main` into `ios-app`, carrying the verdict. One row per **merge**, never one per change.
3. **A test that forces both to be looked at** (Section 4). `ios/SPEC.md` pins a parent version; when `main` moves and is merged here, the branch goes red until somebody reads Section 1, decides, and bumps the pin.

The redness is the feature. Nothing here depends on anybody remembering to do anything.

---

## 0. How to use this document

**When a merge from `main` comes in.** Take the diff of `main` since the last row of Section 3 and ask one question of it: does it touch anything named in Section 1? Section 1 is short and every entry names files and sections, so this is a scan and not a study. Section 2 exists so that a reader can stop looking — it names what is deliberately _out_, and why that was checked rather than assumed.

- **Nothing on the surface moved.** Write the row, bump the pin in `ios/SPEC.md`'s front matter, done. That is the common case and it should stay cheap.
- **Something moved.** The merge commit message carries the reasoning — what changed, what it costs here, what was done about it. The row in Section 3 carries the verdict and points at that commit. Do not copy the reasoning into the row; a row that grows into a paragraph is this file turning into the change log it exists to avoid.

**What this document is not.** It is not a change log, not a mirror of `SPEC.md`'s changelog, and not a list of debugging steps. If a future reader is tempted to "improve" Section 3 into one row per change, the reason it is one row per merge is written into Section 3 itself: one row per merge is what makes the record affordable, and affordable is what makes it get written.

**Keeping this file true.** Section 1 is derived from `ios/SPEC.md`, which is the authority on what the app needs. When `ios/SPEC.md` changes what the app depends on, Section 1 changes in the same commit. When something on the surface changes on `main` and the iOS side is amended in response, both the amendment and the row happen in the same merge.

**I7, in this file's own terms.** `ios/SPEC.md` Section 1's I7 confines `ios-app` to `ios/` and `packages/tracker/`: it reads everything named in Section 1 below and writes none of it. So the only direction a change can flow between the two branches is `main` → `ios-app`, and the merge record of Section 3 is the whole record of that flow — there is no second record of a change flowing the other way, because I7 does not let one exist. What the app needs _from_ `main` — the amendments of `ios/SPEC.md` Section 14, and everything else on "The list for `main`" in `ios/SPEC.md` Section 12 — is applied on `main`, in a separate session, reviewed as website work, and reaches this branch the same way everything else on `main` does: by merge.

### Two directions, two channels

**From `main` to the app.** A web fix reaches the app two ways, and the first needs nobody to do anything. **(1) At runtime:** the app's web view loads the web app from `PUBLIC_ORIGIN` (`ios/SPEC.md` 4.1), the same deployment every browser gets, so a fix deployed to the Pi is in the app the next time it opens — every screen, every piece of copy, every game rule the server applies. **(2) By merge, for the tracker's dependencies:** what the tracker itself depends on is the surface in Section 1, and that reaches the branch only by merging `main` into `ios-app`. The cadence is a rule: merge `main` into `ios-app` after every `SPEC.md` version bump on `main`, and at least once a week while both are active. Under I7 the merge is conflict-free by construction — the branch never touches the files `main` changes — so the cost of a merge is the Section 3 row and the pin bump, and nothing else.

**From the app to `main`.** Building and debugging the app will find things wrong with the web app too. Those are **not** fixed on this branch (I7). Each one is filed as a GitHub issue on the repository, labelled `from-ios`, at the moment it is found — because an issue reaches whoever is working on `main` immediately, while anything written in `ios/` reaches `main` only when the branch merges, which is weeks away. The issue is the notification; a one-line entry under "Found while building the app" in `ios/SPEC.md` Section 12 is the durable record, and the two carry the same words. The list for `main` in that same section — what `main` must do _for_ the app — is the same channel in the other direction: each entry is filed as an issue labelled `for-ios` when `main` is ready to take it up, so `main`'s session has a queue and not a document to mine.

## 4. The pin, and the test that enforces it

The front matter of `ios/SPEC.md` carries a `**Parent:**` line naming the root `SPEC.md` version that document was last checked against — v1.58 today. That is the pin.

`packages/shared/src/ios-parent-pin.test.ts` asserts three things — that the pin exists, that the root `SPEC.md` states a front-matter version, and that the two are equal. It is a new file rather than an edit to `packages/shared/src/spec-version.test.ts`, deliberately: that file exists on `main` and is edited there, and a test that lives only on this branch has no merge surface at all.

The first assertion is not redundant. A test that only compared the two strings would pass when the pin line was deleted, which is the failure this whole arrangement exists to prevent: an invisible decoupling that looks like agreement.

**What the redness means.** When `main` moves and is merged here, this test fails. That is not a version-string mismatch to paper over — it is this branch refusing to pretend a decision was made. Clearing it means doing the three steps in Section 3, in that order. The failure message says so, because whoever meets it will not have read this conversation.
